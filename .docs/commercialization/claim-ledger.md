# Milestone 7 Commercialization Claim Ledger

## 1. Purpose and status

This is a Milestone 7 commercialization planning artifact for the Governed Execution project. It records what can be said, demoed, qualified, deferred, or forbidden based on current repository evidence.

This ledger does not widen Execution Substrate, Control Plane, or Infrastructure Manager contracts. It does not make proof artifacts, reports, traces, logs, retained bundles, readiness reports, support bundles, generated profiles, local process records, or `.out` material authoritative. It does not claim production readiness.

This ledger uses "Milestone 7" as a project commercialization planning label supplied alongside the MVP roadmap and context. It is not an ES `PLANS.md` workstream declaration, and if ES `PLANS.md` does not list Milestone 7, that absence is intentional for now. The ledger remains a commercialization guardrail, not engineering planning authority. Repo-backed implementation claims still defer to ES, CP, and IM governing docs and the Milestone 0 MVP freeze.

The current commercialization positioning is:

- Product category: governed execution boundaries for accepted ES-backed autonomous software work in the current bounded MVP slice.
- First buyer or user profile: security-conscious platform, infrastructure, or security engineering teams evaluating autonomous coding or automation agents for repository work, internal automation, infrastructure changes, or regulated operational workflows. This is a product-positioning hypothesis, not a repo-validated market fact.
- Painful failure mode: autonomous agents can act faster than existing controls, logs, and human approval processes can keep up. This is a commercialization problem statement that needs external validation before being presented as a market fact.
- Refined promise: for accepted ES-backed governed execution paths, execution is admitted through ES-owned contract and preflight gates, handed to a bounded runtime profile through runtime-profile compatibility and handoff boundaries, observed through lifecycle evidence, eligible for guarded CP controls and ES or provider stop requests, retained as opaque result material when produced, and reviewable through CP-owned workflow state plus explicitly non-authoritative evidence. This is bounded runtime-profile isolation in the current MVP slice, not a general sandboxing, full rootless, or least-privilege guarantee.
- What this is not: another AI coding agent, a chat UI, an Okta or Microsoft Entra replacement, a Temporal replacement, a LangSmith replacement, a generic workflow builder, a general deployment platform, or a full enterprise IAM layer.

The ledger uses the redesign-phase classification vocabulary from the governing docs. A claim can be commercially useful and still be only a product-positioning claim. A claim can be repo-backed and still require a qualifier before public use.

## 3. Claim status vocabulary

### Statuses

- `can say now`: The claim is directly supported by stable docs, bounded MVP proof docs, code-backed inspection, or repo-owned contracts, and does not require live validation to state in qualified form.
- `can demo after validation`: The claim can be part of a demo only after the relevant local proof, dry run, or non-live validation evidence is collected for that demo instance.
- `can say only with qualifier`: The claim is repo-backed only within a bounded path, compatibility edge, MVP slice, or evidence/projection scope. The qualifier is required in public wording.
- `roadmap / later integration`: The claim is an allowed posture or future integration direction, not an implemented repo-backed capability.
- `must not say`: The claim contradicts current repo authority, overstates production readiness, promotes evidence into authority, or assigns ownership to the wrong repo or surface.
- `source gap / needs validation`: The claim may be strategically plausible, but current repo evidence is insufficient. It needs external source validation, market research, live proof, or an explicit design decision before use.

### Evidence levels

- `stable contract`: An authoritative doc currently defines the behavior as a retained contract or boundary.
- `bounded MVP proof`: The behavior is part of a bounded Milestone 0 or MVP proof slice and must not be generalized.
- `compatibility edge`: The behavior is retained for compatibility and should stay explicitly labeled as temporary or bounded.
- `evidence/projection`: The surface reports, summarizes, mirrors, exports, or projects state but is not orchestration, lifecycle, security, scheduler, or run-control authority.
- `implementation detail`: Current code shape exists but is not itself design authority for cross-service semantics.
- `reopened seam`: An architecture-defining surface that remains open for re-derivation under `PLANS.md`.
- `docs-only inference`: A planning or commercialization inference drawn from repo docs, not directly implemented as behavior.
- `code-backed inspection`: Source code confirms the current shape or schema.
- `test-backed inspection`: A repo test or proof explicitly checks the behavior.
- `validation required`: A demo-specific claim is source-grounded in the repos but still needs a concrete dated artifact, run summary, proof file, or validation output before it can be shown externally.
- `external-source-required`: Market, buyer, regulatory, competitor, or integration claims that require current external citations outside these repos.

## 5. Allowed public wording

- Governed execution boundaries for accepted ES-backed autonomous software work in the current bounded MVP slice.
- We are not another AI coding agent. We provide governed execution boundaries for accepted ES-backed risky autonomous work in the current bounded MVP slice.
- Execution Substrate admits work through declared compatibility and preflight surfaces, hands accepted work to a bounded runtime profile, projects lifecycle evidence, and retains opaque result bundles.
- Control Plane is the current reference UI and orchestrator for workflow-owned review, intervention, and finalization; it does not define ES execution contracts.
- Retained result material is kept as opaque ES output. CP owns semantic interpretation, review, and finalization.
- The agent is not the authority. The chat, browser, app, iMessage, or channel surface is not the authority.
- Support bundles, logs, traces, reports, readiness reports, retained bundles, and `.out` material are evidence, not run truth.
- Supported ES-backed attempts can receive guarded stop requests; later lifecycle projection is what proves the observed terminal outcome.
- Accepted ES-backed paths are reviewable with CP workflow state and supporting non-authoritative evidence.
- Infrastructure Manager supports bootstrap, readiness, provenance, diagnostics, and redacted support evidence. It does not control governed runs.
- Remote Alpha is a bounded pre-live readiness and support posture, not production, HA, multi-tenant, or general remote deployment.
- Future enterprise identity and observability integrations should preserve ES authority boundaries instead of replacing them.

## 9. Maintenance rules

- Every new marketing, website, sales, demo, GUI, operator-console, or integration claim must map to a repo source, a claim status, an owner repo or surface, and a required qualifier if applicable.
- Every authority-affecting claim must identify the owner repo. ES owns governed execution contracts and handoff boundaries. CP owns orchestration, review, intervention, and workflow state. IM owns bootstrap, readiness, provenance, diagnostics, and support evidence.
- Evidence/projection artifacts must not be promoted to authority. This includes traces, reports, logs, readiness reports, support bundles, retained bundles, generated profiles, local process records, proof outputs, and `.out` material.
- Support bundles used externally must be redacted and shareable; they must not expose raw logs, prompts, diffs, workspaces, credentials, TLS/SPIFFE/SPIRE/Vault material, API keys, WebAuthn/passkey material, SQLite state, sensitive local process records, or raw retained bundles.
- Claims relying on external market facts, buyer urgency, competitor positioning, regulatory needs, or vendor integrations require current external citations outside these repos before public use.
- Roadmap and later-integration claims must remain clearly separated from implemented claims.
- Compatibility-heavy behavior must remain explicitly labeled, especially `control-plane-normal-shell/v1` and Remote Alpha posture.
- Reopened seams must not be described as settled architecture unless `PLANS.md` and the relevant `.docs/` pages have been updated first.
- Before an external demo, re-run or collect the validation evidence listed in this ledger for the exact demo path, then update the checklist.
- Do not update this ledger by turning marketing language into architecture. If a claim requires implementation or contract changes, update the governing docs and tests first under the repository rules.
